# CI-down image admission

`github-actions-v1` remains the normal image-build and promotion trust mode, but callers must select it explicitly. When GitHub Actions is unavailable, release operators may select `aws-kms-ci-down-v1` explicitly in `promote-verified-image.py` and `resolve-trusted-image.py`; neither tool silently falls back between modes.

The alternate path does not trust CodeBuild merely because it ran in AWS. Contract schema 1.1 assigns four distinct KMS signing authorities to the coordinator, `amd64` builder, `arm64` builder, and promoter. A signature made by one role is never valid for another role's artifact. `.github/scripts/ci_down_admission.py` requires this canonical chain:

1. A coordinator-signed canonical-job ledger for the exact clean source commit, tree, main ref, build cohort, admission nonce, and every ordered phase for every image: native child build, promoter index seal, per-architecture post-index receipt, then promotion.
2. A promoter-signed sealed-index record that binds the final OCI index digest to both native child digests, the exact ledger, build plan, image, repository, cohort, and pinned promoter job.
3. One `amd64`-signed and one `arm64`-signed post-index receipt for that same seal. Each receipt binds the seal digest, final index digest, native child digest, and fresh provenance, SPDX SBOM, Trivy 0.70.0 report/database metadata, and admitted quarantine disposition. Evidence must predate the seal; the post-index receipt must not.
4. A promoter-signed, monotonically versioned consumed-cohort ledger plus image-bound reservation claim. Before invoking any per-image promotion, the promoter stores the ledger payload and its signature together in one canonical envelope and advances that one versioned S3 object with `If-Match` on the exact prior ETag (`If-None-Match: *` only for first creation). It reads the committed version back byte-for-byte. A stale writer reloads and rebases so distinct cohorts cannot be lost; an identical cohort or a persistent lost race fails before any registry mutation. The per-image claim is then conditionally created at its deterministic object with `If-None-Match: *`, preventing any image/cohort reservation from mutating the registry twice.

Every JSON input must be canonical (`sort_keys`, compact separators, one trailing newline). The build ledger, seal, receipts, and claims have detached canonical signature envelopes; the consumed-cohort ledger embeds the same exact signature-envelope shape beside its payload so both cross the S3 commit point atomically. Each signature envelope contains:

- `trust_mode: aws-kms-ci-down-v1`
- the pinned KMS key ARN
- the SHA-256 fingerprint of the DER public key
- `signing_algorithm: ECDSA_SHA_256`
- the payload SHA-256 and base64 KMS signature

The four KMS key ARNs and public-key fingerprint/artifacts, four builder identities, and authoritative cohort-store prefix are not command-line inputs. They come only from the reviewed `.github/release/ci-down-trust-policy.json`; even the standalone diagnostic CLI has no trust-policy override. All four authorities must have distinct key ARNs, DER fingerprints, and pinned public-key paths. That policy is committed disabled and therefore fails closed until a separate provider-infrastructure change installs the exact keys, identities, and store and enables it.

Admission is restricted to `refs/heads/main`, exact 40-character commit/tree identities, fresh receipts and scanner database metadata, the exact committed build-plan SHA/generator/matrix, an OCI index fetched by digest whose native child descriptors match the seal and both receipts, immutable tags, and one pinned native builder identity per architecture. The verifier refuses dirty sources, plan drift, mixed cohorts, cross-role signatures, key or fingerprint substitution, schema downgrade, pre-index receipts, missing or duplicate phases, duplicate receipt identities, replayed cohorts, stale evidence, non-native builders, evidence digest drift, nonzero High/Critical findings, missing/duplicate/extra OCI platforms, and conflicting immutable tags.

The committed build-plan generator is used by the normal build workflow and by the CI-down build coordinator. The reviewed provider definition lives in `infrastructure/cloudformation/ci-down-release-builders.yaml`; its committed buildspecs and phase runners live in `infrastructure/ci-down-release/`. The stack keeps the coordinator, native amd64 builder, native arm64 builder, and promoter in distinct CodeBuild roles with distinct KMS signing keys. The coordinator cannot call `codebuild:StartBuild`, because that API permits source and buildspec overrides under the target project's signer. It can only start a fixed Step Functions graph whose non-signing role has no KMS, ECR, S3, deployment, or secret access. That graph runs two native child builds, promoter index seal, two native post-index receipts, then promoter admission and immutable tagging. Neither the template nor its roles can deploy the platform.

Landing that provider definition still does not create or mutate AWS resources. A separate reviewed PR must deploy it, capture the live project and KMS identities, export the four public keys, commit their exact DER fingerprints, verify the versioned cohort-store readback, and only then enable `.github/release/ci-down-trust-policy.json`. Until that PR lands, `CI_DOWN_RELEASE_AUTHORIZED` defaults to `false` and the policy remains disabled.

`update-stack.yml` keeps `github-actions-v1` as its explicit default. Selecting `aws-kms-ci-down-v1` requires a canonical evidence bundle and the reviewed SHA-256 of the repository policy. The workflow derives fixed plan/ledger and per-image seal, receipt, signature, OCI-index, and claim paths from that bundle; the resolver then compares the retained index with bytes fetched from the registry before admission. Missing evidence, a changed policy digest, or a mode mismatch fails before a stack update.
