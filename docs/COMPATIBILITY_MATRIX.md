# SDK-Platform Compatibility Matrix

This document maps platform versions to minimum SDK versions and the features each release introduced.

**Current (platform 10.4.0):** minimum SDK **8.0.0** (Go/Python/TypeScript/Java; Rust **0.7.0**), recommended SDK **9.3.0** (Go/Python/TypeScript/Java; Rust **0.10.0**). These floors are what the platform `/health` endpoint advertises (`min_sdk_version` / `recommended_sdk_version`). None of 10.1.0, 10.2.0, 10.3.0 or 10.4.0 moved the minimum map - **10.4.0 deliberately does not, because an ABSENT PEP capability handshake is the legacy caller the platform still serves**, so a client below the recommended version loses the declaration and not the service. **10.4.0 moves the recommended map** to the 9.3.0 / 0.10.0 releases carrying the read-path identity scoping and, in Python, the `extra_headers` attach point; the bump is made in the release-prep commit so the release's own images advertise it, and the tags are cut AFTER the community platform release, per `RUNBOOK_PLATFORM_RELEASE.md`'s ordering. **10.3.0 moves the recommended map:** the v9.2.0 / v0.9.0 SDK releases carrying the AuthZEN-native surface are tagged and published to every registry, and the recommended-map bump advertising them (#3650) is part of the v10.3.0 cut itself. (An earlier revision of this paragraph, written before publication, said the recommended map stayed at 9.1.1 Go / 9.1.0 elsewhere / Rust 0.8.2 because no tag had been cut; the tags and the map bump both shipped with v10.3.0.)

**The 10.0.0 platform major does NOT move the SDK floor.** The Go, Python, TypeScript and Java floor stays at 8.0.0, as it has continuously since v7.9.0 and across the v8.0.0 and v9.0.0 platform majors before it. The Rust floor stays at 0.7.0, which is the only value it has ever held: Rust was absent from `MinSDKVersion` at v7.9.0, v8.0.0, v9.0.0 and v9.6.1, and joined the compatibility maps at v9.7.0 (see the v9.7.0 row below). A platform major and an SDK floor are independent axes on this platform: the floor moves only when the platform stops speaking a wire contract an older SDK depends on, which 10.0.0 does not do.

> **Note on version numbers:** SDK versions are deliberately decoupled from platform versions. The Go SDK's module path tracks its major: SDK 8.x is `github.com/getaxonflow/axonflow-sdk-go/v8`, SDK 9.x is `.../v9`. The Rust SDK is on an independent 0.x line (currently 0.10.0) and does not carry the 9.0.0 LangGraph/computer-use adapters. Its caret is **minor**-locked, so a dependant pinned `"0.9.0"` does NOT pick up 0.10.0 and has to be edited - unlike a 1.x pin, where the caret would absorb it.

## Upgrade Guidance

- **Always upgrade the platform before or alongside SDK upgrades.** New SDK features may call endpoints that only exist in newer platform versions.
- The SDK 9.0.0 majors send the MCP server/tool identity as a separate `tool` wire field (no longer concatenated into `connector_type`). The platform accepts this on check-input from 9.10.0 and on check-output from 9.11.0; older platforms ignore the field.
- If you see a version mismatch warning in SDK logs, upgrade your platform to the recommended version.
- Use `healthCheckDetailed()` / `health_check_detailed()` to programmatically check what the platform supports before using new features.

## Backward Compatibility Guarantees

| Scenario | Behavior |
|----------|----------|
| **Old SDK + New Platform** | Safe for field ADDITIONS: old SDKs ignore unknown JSON fields. Exception: the v9.0.0 canonical-verdict cutover changes `policy_decision` values an integrator reads back - see the v8 → v9 migration guide. Exception: v10.0.0 changes what several read APIs put on the wire when they have nothing to report, and this is the same break set the v10.0.0 row above enumerates. In full: (1) `avg_latency_ms` becomes nullable on the audit report/summary and session-summary, and `tokens_used`, `cost` and `response_time_ms` are OMITTED rather than sent as `0` on audit search/export/get, so any client binding them to a non-optional number breaks; (2) the LEGACY `POST /api/v1/sebi/audit/export` gains `status: "partial"` and omits `summary.compliance_score` on an incomplete export, so an integration on that route keyed on `status === "completed"` breaks - note `POST /api/v1/compliance/reports` is a separate contract whose status vocabulary does NOT change and never returns `partial`; (3) declarative-workflow run ids from `POST /api/v1/workflows/execute` change prefix from `wf_` to `wfe_`, so **a client that prefix-matches `wf_` on those ids stops matching** - the ids stay opaque and nothing in the platform parses them, and ids minted before this release keep their old prefix; (4) `POST /api/v1/audit/report` now returns `500` where it previously returned a silently short top-policies table; (5) a `/api/v1/unified/executions` list carrying neither a tenant nor an org key is now `401` rather than an unscoped `200`; (6) on the MCP-server `check_policy` / `check_output` tools, an organisation holding an enabled segment-scoped policy must now send `X-User-Token` or the call is refused. |

## PEP capability handshake (clients)

`X-Axonflow-PEP-Handshake`, profile 1. ADR-065; design
`technical-docs/PEP_CAPABILITY_HANDSHAKE.md`.

**Platform >= v10.4.0 reads it** on `/api/v1/decide` and
`/api/v1/access/evaluation` (#3704), and on `/api/v1/mcp/check-input`,
`/api/v1/mcp/check-output` and the `/api/v1/mcp-server` governance tools
(#3766). **Older platforms ignore the header entirely and behave exactly as
before**, so a client listed here is safe to deploy against any platform
version.

**Every client below is OPT-IN and off by default.** The declaration is
presented only when `AXONFLOW_PEP_AUDIENCE` is set, because the audience is
what a decision proof gets bound to and only the deployment knows it. Unset
sends no header at all, and the client behaves byte for byte as its previous
release did.

**The `Declares` column is the point of this table.** A client declares the
obligation types it can actually discharge, and discharging `field_redact`
means substituting the platform's engine-masked text for the original -
ADR-056 forbids a client from redacting for itself. A client that performs no
substitution declares the empty set, so that on an Enterprise platform the
request is **denied** rather than allowed on the strength of a substitution
nobody performs. That is ADR-065 invariant 8, and it is why the honest answer
for several clients is "nothing".

| Client | Min version that handshakes | Enforcement point(s) | Declares | Basis |
|---|---|---|---|---|
| `axonflow-claude-desktop-plugin` | **0.4.0** | `claude-desktop-plugin` | `field_redact@1`, or `[]` under `AXONFLOW_REDACT_RESPONSES=off` | calls the fulfillment endpoint and forwards the engine-redacted content; under `off` it never calls it, so it declares nothing |
| `axonflow-openclaw-plugin` | **2.9.0** | `openclaw-request`, `openclaw-response` | both `field_redact@1` | the response path substitutes `redacted_data`; the request path substitutes `redacted_statement` as of the same release |
| `axonflow-claude-plugin` | **1.12.0** | `claude-code-plugin` | `[]` | hooks submit a statement and act on the verdict; no substitution |
| `axonflow-codex-plugin` | **1.8.0** | `codex-plugin` | `[]` | as above |
| `axonflow-cursor-plugin` | **1.8.0** | `cursor-plugin` | `[]` | as above |
| `axonflow-n8n-node` | **1.2.0** | `n8n-node` | `[]` | returns the platform's response to the workflow, which decides; the node cannot promise a substitution on a workflow's behalf |
| `axonflow-google-adk-plugin` | *pending* | `adk-request`, `adk-response` | `[]` and `field_redact@1` | the response path round-trips `redacted_message`; the request path does not substitute. Requires `axonflow-sdk-python` >= 9.3.0 |
| `axonflow-litellm` | *pending* | *(via the Python SDK)* | *(per its discharge table)* | reaches the platform only through `axonflow-sdk-python`; requires >= 9.3.0 |
| `platform/gateway-adapters` | ships with the platform | `ext_authz`/`ext_proc` seams | `field_redact@1` (body-capable), `[]` (headers-only) | shipped in #3708, opt-in behind `AXONFLOW_PEP_AUDIENCE` |

**Two clients present TWO declarations, and that is deliberate.** One process
can be two enforcement points whose paths discharge different obligations, so
each path presents its own document under its own `pep_id` and the platform
composes a separate identifier for each. A single document for both would
either over-claim on one path (the platform allows, believing an obligation
will be discharged) or under-claim on the other (a working path is denied).
This is the case the per-request carrier exists for, and the gateway adapters
were its first instance.

**A note for operators enabling this.** On an **Enterprise** platform, a client
declaring `[]` is **denied** a request carrying a mandatory redaction
obligation, where before it was allowed. That is the intended change and it is
why the header is opt-in. On a **Community** platform nothing is denied either
way: the capability deny is `enterprise_implementation` and is physically
absent from that build, so the declaration is read, bound and counted only, and
`axonflow_pep_handshake_total{plane=...}` is what makes a capability gap
visible there.

## Capability Discovery

Starting with platform v4.8.0, the `/health` endpoint returns a `capabilities` array listing all supported features, plus `min_sdk_version` / `recommended_sdk_version` maps. SDKs can use this for runtime feature detection:

```go
// Go
health, _ := client.HealthCheckDetailed()
if health.HasCapability("mcp_check_endpoints") {
    // Safe to use MCP check endpoints
}
```

```python
# Python
health = client.health_check_detailed()
if health.has_capability("mcp_check_endpoints"):
    # Safe to use MCP check endpoints
    ...
```

```typescript
// TypeScript
const health = await client.healthCheck();
if (AxonFlow.hasCapability(health, 'mcp_check_endpoints')) {
    // Safe to use MCP check endpoints
}
```

```java
// Java
HealthStatus health = client.healthCheck();
if (health.hasCapability("mcp_check_endpoints")) {
    // Safe to use MCP check endpoints
}
```

Capabilities added in recent releases include `client_version_telemetry` (9.7.0), `identity_header_attribution` (9.9.0), and `seam_capability_decisioning` (9.11.0).
